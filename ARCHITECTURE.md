# Architecture

How peon-code works inside. For what it does from the user's side, see [README.md](README.md).

`lib/deps.sh` shares tmux 3.2+ and Python 3.10+ version checks across the installer and launchers; the runtime checks never install packages.

## Adding a CLI

Steps:

1. Copy a provider file in `lib/cli/` to `<name>.sh`, where `<name>` is the bare command name, such as `foo`, the first word of the agent command; a path such as `/opt/bin/foo` in the agent command matches no provider.
2. Rename its functions with the `<name>_` prefix and fill each concern below.
3. Run `tests/test_peon_code.sh`.

`lib/cli.sh` loads every file in that directory. `cli_call <bin> <concern> args...` selects its function with `declare -F`; an unknown CLI keeps a positional prompt and has no trust, transcript store, context parser, placeholder, or known prompt marker.

The shipped providers launch and resume this way:

| CLI | Launch | Resume |
|-----|--------|--------|
| claude | a `--settings` file for the normal screen; the brief is pasted once the TUI is up | `--resume <id>` |
| codex | the brief as a positional prompt, plus `--no-alt-screen`; it stays interactive | `resume <id>` |
| copilot | `-i <prompt>` | `--resume=<id>` |
| gemini, qwen | `-i <prompt>` | `--resume <id>` |
| grok | the brief as a positional prompt | `--resume <id>` |
| any other | the command as given, brief appended as a positional prompt | none |

### Per-pane provider selection

The launch stores each pane's binary in the `@peon_bin` pane option. When `lib/cli.sh` is sourced, it joins every provider's marker into `CLI_ALL_PROMPT_MARKERS` (`|`-separated) and collects every placeholder into `CLI_ALL_PASTE_PLACEHOLDERS`. `cli_select_pane <pane>` reads that pane's `@peon_bin` and sets the working globals `CLI_PROMPT_MARKERS`, `CLI_PASTE_PLACEHOLDERS`, and `CLI_PANE_HAS_PROMPT_MARKER` for that provider alone. Marker and placeholder fall back to the `CLI_ALL_` values independently, so a provider with a marker but no placeholder still matches every known placeholder. A pane with no `@peon_bin`, such as one from an older launch, gets the merged values and counts as having a marker. A pane whose provider prints no marker, such as gemini or an unknown CLI, gets the merged markers and `CLI_PANE_HAS_PROMPT_MARKER=0`; its placeholder list is the merged one only when the provider prints no placeholder either.

The globals are per call, not per pane, so each entry point selects before it parses: `with_pane_delivery` in `lib/delivery.sh` (around every locked paste, send, slash command, key, rebrief, and `launch_command_locked`, the launch-command paste that `lib/launch.sh` and the watcher's restart share), `pane_box_ready` in `lib/input.sh`, and `answer_dialog` and `wait_pane_settled` in `lib/tmux.sh`. The awk parsers in `lib/input.sh` (`pane_has_menu`, `pane_free_text_number`, `strip_styles`, `pane_box_text`) and `box_is_paste_placeholder` read the globals and rely on that earlier selection.

`wait_pane_settled` uses the marker when the pane has one: it returns once two consecutive captures match and contain a marker. A pane without a marker returns after three identical captures that are not blank, about 0.6 s. Either way a capture that holds a menu does not count, and the call returns 1 after the tries cap (100 tries of 0.3 s by default). The only startup caller is `claude_brief_after_start`, and claude has a marker, so the no-marker branch runs only in the wait before the rebrief that follows `compact` or `clear` (`lib/commands.sh`). It is reached only when the provider declares no marker but the pane draws one of the merged markers: the input-box parsers need a marker on screen, so `send`, `rebrief`, `compact`, and `clear` refuse a pane that draws no marker peon-code knows before any wait.

Every provider defines `launch_command`, `trust_project`, `resume_dir`, `resume_id`, `context_tokens`, `paste_placeholder`, and `prompt_marker`; `usage_tokens`, `weekly_limit`, `compact_count`, `resume_args`, `own_thread`, `child_threads`, `swap_args`, `probe_command`, and `quit_command` are optional (see [Usage report](#usage-report), [Weekly limit](#weekly-limit), [Context watcher](#context-watcher), [Resume lookup](#resume-lookup), and [Swap](#swap)). `own_thread` takes a transcript path and returns 1 to reject it as a subagent thread; its fallback returns 0. `child_threads` prints the child transcript paths of a transcript, one per line; its fallback returns 1, meaning none. `swap_args` prints the model and effort flags to append, `probe_command` the headless check command, and `quit_command` the slash command that ends the agent. `resume_args` prints the arguments that resume its quoted id argument, with a leading space; claude and codex define it and use it in their own `launch_command`, and a CLI without it returns 1, so the watcher restarts that CLI fresh. `launch_command` prints the shell command and takes the binary, argument string (with its leading space), quoted resume id, quoted prompt expression, and pane index. `trust_project` takes the physical and logical project paths. `resume_dir` sets the caller's local `dir` and optional `cwd` filter; `resume_id` prints the id from its transcript path argument. `context_tokens` prints the last request's context size from its transcript path argument; without arguments it returns 0 when supported and 1 when unsupported. The optional `compact_count` takes a transcript path and prints its number of compaction boundaries; providers without this hook skip boundary tracking. An unsupported parser called with a transcript returns 0 with no output. `paste_placeholder` prints its anchored regular expression. `prompt_marker` prints one literal marker or a `|`-joined list, or nothing when unknown. Markers contain no regular-expression metacharacters. Claude reports `❯|!`: its shell-mode `!` counts only in column zero, so punctuation inside text and the indented shell-mode footer do not count as prompts. The box reader returns the shell command with status 5. Before a paste, send, message, brief, and slash-command callers refuse this status. After a send paste, status 5 is accepted only when the message starts with `!` and the box equals the command after that leading `!` is removed and whitespace is normalized. An explicit `key --submit Enter` can submit a non-empty shell command.

A provider whose brief follows TUI startup can also define `brief_after_start`; Claude uses it for its folder-trust dialog, resume picker, and delayed paste. It reads the existing globals `i` (pane index), `RID` (resume id), `BRIEF` (prompt text), `NAMES`, and `PANE_IDS`, and writes `PASTE_RC` for the paste result. Other providers need no function for this concern. `tests/test_peon_code.sh` checks all seven required functions, the marker character contract, generic launch behavior, per-pane marker and placeholder selection (`test_cli_pane_selection`), and both settle rules (`test_cli_pane_settled`).

## Pane identity

Each agent pane carries its name in the `@peon_name` tmux pane option and its brief file path in `@peon_brief`, both set at launch; an app cannot overwrite a pane option, unlike the pane title, so the pane border shows `@peon_name` too. Every subcommand acts only on panes carrying `@peon_name`, and the session-scoped ones only on sessions marked `@peon_code`.

## Pasting

Text goes in through a tmux buffer as a bracketed paste, so a multi-line message stays in the input line instead of submitting early.

`compact` and `clear` call `slash_then_rebrief` in `lib/commands.sh`. Before a slash paste, `slash_locked` rejects copy mode, an active turn, a menu, and typed input. For `/compact`, it sets `@peon_compact_owned` to 1 after these checks and before the paste, and clears it if the paste or submission fails. `pane_is_busy` in `lib/tmux.sh` uses the shared set of known prompt markers to find the last prompt line. It checks only the four non-blank rows above that line for a working row that starts with a spinner glyph, has at most 40 characters between that glyph and the opening parenthesis, and opens those parentheses with elapsed seconds or minutes and seconds. Long replies and wrapped quotes higher in the output do not match. This is one elapsed-time shape for Claude and Codex; a CLI without it needs a provider concern. After the slash is submitted, the command polls for both a settled screen and no working row within one 120-second cap. If the pane stays busy, it sets the pane option `@peon_rebrief_pending` to 1 and leaves the brief unsent. A running watcher checks pending briefs every tick, before the transcript read gate. It waits up to 10 settle tries, checks the working row again, sends the stored brief through `rebrief_pane`. `rebrief_locked` clears the option itself after a confirmed paste, and the watcher clears it on status 5 (Enter sent, submission not confirmed). Success logs `<name> brief re-sent after compaction` once. Status 5 logs `<name> brief submission not confirmed after Enter; automatic retry stopped` once. Clearing the option after an unconfirmed Enter prevents the next watcher pass from sending the full brief again.

`rebrief <name|all> [<session>]` runs `rebrief_agents`, which walks the agent panes from `list_agent_panes` in `lib/tmux.sh`, so a pane at a shell is not a target; a named agent found only at a shell gets an error that its brief is pasted when it restarts. It skips the caller's own pane, `TMUX_PANE`, and prints the command to run once that pane is free, because a pane cannot paste into its own input box while it runs a command. Each other pane goes through `rebrief_pane`, which runs `rebrief_locked` under the pane's delivery lock. `rebrief_locked` checks the stored brief file and the pane identity, refuses a pane that `pane_is_busy` reports busy, a box that holds typed text, and a dialog or a menu, all with status 3, and pastes the brief only into an empty box. A confirmed paste clears `@peon_rebrief_pending`, so a manual rebrief also ends a pending watcher retry. The command exits nonzero when no brief was confirmed or when any paste was left unconfirmed.

Every paste, key, and slash command to a pane runs under `with_pane_delivery` (`lib/delivery.sh`), which takes a per-pane lock by `mkdir` of `/tmp/peon-code-delivery-$UID/<key>`, where `<key>` is the `cksum` of the tmux socket path and pane id. The root is created under `umask 077`, and a root that is not a directory owned by the user, or is a symlink, is refused with exit 75. A held lock is retried every 0.2 s up to 25 times, about 5 seconds, then refused with exit 75 and a message that prints the lock path. A caller that already holds the lock runs its command directly. The lock directory holds an `owner` file with the guard's pid, which nothing reads, and an EXIT trap removes both on a normal exit. A lock left by a killed delivery is treated as held, since a tmux child of the killed guard might still be running, so it is removed by hand: after confirming no delivery to that pane is running, delete the `owner` file and the empty directory at the printed path. `web/server.py` also serializes the browser's send, swap, key, and explain requests behind one server-wide lock.

## Browser workspace

`peon-code-web.sh` resolves its install symlink and starts the optional Python stdlib server. `web/launch.py` owns CLI parsing, platform browser opening, and the single-command SSH workflow; port 8765 is its canonical default. Without `--port`, the local server chooses a free port when 8765 is busy. Without `--port`, SSH forwards the `PORT_RANGE` of twenty ports 8765-8784 (`web/launch.py`) in one connection, one loopback-only `-L` per port, under `ExitOnForwardFailure=yes` (`ssh_command` in `web/launch.py`). The remote command gets `--port 8765 --port-range 20` (`ssh_command`); `--port-range` is a hidden option, and the parser refuses a range that is empty, passes 65535, or follows `--port 0` (`arguments` in `web/launch.py`). Before ssh starts, `remote_ui()` binds a probe socket on each local candidate; a busy local port maps to a free ephemeral one, with a note on stderr. The probes close when the `ExitStack` block ends, before `Popen`, so a port taken in that gap fails the forward and the launch. On the agent host, `bind_server(port, port_range)` in `web/server.py` walks the candidates in order. Every server writes `web-<port>.url` (mode 0600) next to `web-<port>.pid` in `~/.config/peon-code`: line 1 is its launch URL, line 2 its kind, `local` or `ssh` (`main()`). At exit a server removes its pid file, and a local server also removes its url file; an `ssh` server leaves its url file, so the token outlives it on the host. A busy candidate whose pid file names a running `web/server.py` process is judged by that url file (`read_server_url()`). A local start (`replace=False`) reuses a live `local` server, printing its URL with `Server was already running.`, opening it, and exiting without stopping it; it skips any other server. The `--stdio` (SSH) path skips a live `local` server, or one whose url file has no kind line, and stops a live `ssh` server, or one with no url file, with SIGTERM and takes its port; any other busy candidate is skipped on both paths. On every port the `--stdio` path binds, a leftover url file of kind `ssh` hands its token to the new server, so a successor serves the same URL; a local server always draws a fresh token. A local reuse opens whatever page the running server serves: the session argument and `--dir` still create or open their team, which joins that page's list, but the page keeps its selected tab, and `--port N` only picks which port to check. With `--stdio --open-only`, `main()` binds no port: it runs `open_project()` for `--dir`, the session, and `--config`, prints `{"session": <name>}`, and exits. On the laptop, `remote_ui()` in `web/launch.py` records a live SSH launch in `~/.config/peon-code/web-ssh-<host>.url` at mode 0600, where `<host>` keeps `[A-Za-z0-9_.-]` and maps every other character to `_`: line 1 the local URL, line 2 the launcher pid, then one `<remote> <local>` line for each port the probe moved to another local port. A new launch to the same host reuses the recorded URL without starting ssh when that pid is a running `web/server.py` process and the URL's local port accepts a connection. When that launch names `--dir`, a session, or `--config`, one ssh call with `--open-only` first creates or opens the team (`open_remote_project()`), after the config upload. At exit the launcher removes the record only when it still names its own pid and holds no remap line. A kept record makes the next launch try the recorded local port of each remote port first, so with the inherited token the URL stays the same. Thus a second SSH launch to the same host, without a live launch on that laptop, replaces the first remote server at 8765 rather than moving to 8766; the range helps only when other programs hold the ports. The remote command names `--port`, so the server never falls back to an ephemeral port, which no forward would reach. When every candidate fails, it raises the error from the first one, and `main()` reports the whole range. The rendezvous check accepts a URL only on one of the forwarded remote ports, then rewrites it to the matching local port (`remote_ui`). Explicit `--port N` pins the local server port, or both ends of an SSH forward, to N, with one forward and no `--port-range` (`ssh_command`). SSH starts the remote installed command with safely quoted arguments and a PATH-independent fallback, validates its JSON launch rendezvous, and opens locally. With `--config PATH`, an extra SSH call first copies the local file bytes to `~/.config/peon-code/uploads/<name>.conf`, using a sanitized session name or project basename. The copy uses `umask 077` and applies `chmod 600` after writing, so an existing upload also gets private permissions. The forwarded command receives that literal `~` path through `--config`; the remote parser expands it on the agent host. The remote user config is unchanged. Remote stdio EOF stops the SSH-owned web server. An unresolved conflict on an explicit port fails before team creation. `--dir PATH` resolves the project on the agent host and derives the default name from its basename; a positional session name overrides it. Without `--dir`, `main()` in `web/server.py` checks a positional session with `tmux has-session`: an existing session is used as is and must have agent panes, and a missing one gets the current working directory as its project, on the local and the `--stdio` path alike, so over SSH it is the login directory on the host. Missing sessions use the existing headless launcher in that directory. The session argument never narrows the page: `server.session` is always `None`, so the page lists every peon-code session on the host, and the named session is only `server.initial`, the tab selected on a fresh start. A supplied config reaches `peon-code.sh -c <absolute path> <session>`, so it takes precedence over the project and user config files. Existing sessions require the peon marker and matching project metadata, falling back to stable session_path for older teams. Reserved launcher-command names cannot trigger creation. The browser **+** tab posts to `/api/open`, which calls the same `open_project()`; a config file, UTF-8 and at most 200 KiB, is written under its own file name to a fresh `mkdtemp` directory `team-*` in `~/.config/peon-code/uploads/`, and the directory is removed when the launch returns (`do_POST` in `web/server.py`).

The new-session form holds a project directory, an optional session name, a **Resume** `select name="resume"`, a **Saved teams** `select name="teams"`, and an optional team config upload (`#new-session-form` in `web/index.html`). **Resume** defaults to **Yes** (`yes`); **No** (`no`) starts fresh. Yes disables **Saved teams** and ignores its value. The **Saved teams** select offers **Launch** (`all`) first and so the default, and **Skip** (`single`). The Resume and Saved teams labels have fixed flex bases of 96 px and 134 px through `label:has(select)` in `web/style.css`, with no growth. Text input labels use a 240 px flex basis and take the free width. The file input label uses a 200 px flex basis with no growth. All five field boxes use `--control-height: 29px`. Start session and Cancel use a 17 px line height with their existing padding and borders, so their 29 px height stays equal to the fields with fallback fonts. The file input uses smaller vertical padding and a compact `::file-selector-button` so its native button fits. At 1280 px, the five labels share one line, and all seven controls share the next line with equal heights and matching top and bottom edges; `align-self: flex-end` places the buttons on that line. The form wraps on narrow windows. A successful submit resets Resume to Yes and disables Saved teams again. On submit `configFields()` reads the upload, at most 200 KiB, into `config_text` with its file name as `config_name`, and the page posts them with `directory`, `session`, `resume`, and `single_team` to `/api/open`; both flags are JSON booleans, and `single_team` is true only when Resume is No and Saved teams reads `single` (`newSessionForm.onsubmit` in `web/app.js`). The `/api/open` branch of `do_POST` in `web/server.py` defaults missing `resume` and `single_team` to false, refuses either value when it is not a bool, and passes them to `open_project()` with `single_team` forced false during resume. `open_project()` in `web/launch.py` builds `peon-code.sh [-c <config>] resume <session>` during resume, so saved teams launch, including with an uploaded config. A fresh start appends `--single-team` only when requested, after any `-c <config>` and before the session name. These arguments apply only to a new session; for a session that already runs it returns before building the command, so the flag has no effect. `/api/team` ignores `resume` and `single_team`. The command-line browser launcher supplies no resume flag and keeps its fresh start. A 409 that carries `create` true asks whether to create the missing folder and posts again with `create`. The page never sends `save` to `/api/open`, so an uploaded config is never kept. The server still accepts it, and refuses `save` without a config, in the `/api/open` branch of `do_POST` in `web/server.py`. It reads no `roles` key, so a request that carries one launches as if the key were absent. With `save` and a config, it derives the session name the way the launcher does and refuses a session that already runs, creates a missing folder only with `create`, and refuses with 409 when `<project>/peon-code.conf` exists, even as a symlink. Without `save`, the config goes to a fresh `mkdtemp` directory `team-*` under `~/.config/peon-code/uploads/`. The file is opened with exclusive create and joins the `written` list as soon as it exists. In the `finally` block, a launch that did not succeed unlinks every path in `written`, and the upload directory is removed in every case; a folder the request created stays.

`web/bridge.py` discovers marked sessions and agent roles, with launch metadata and a brief fallback for older sessions. Session project metadata is recorded at creation; older sessions fall back to pane_current_path via a separate display response preserving whitespace. Its styled display capture uses `-e -N` and keeps physical rows so the browser does not re-wrap soft-wrapped lines and a redraw does not change the row count. It drops trailing blank rows only up to the excess pane height over the browser row count; captures without a browser row count stay unchanged. Plain `screen` and styled `styledScreen` capture visible physical rows without `-J`; menu checks, cursor rows, and input-box and hint parsing use these unjoined screens. Explicit window/active styles apply to the display. `web/ansi.js` renders safe text spans with SGR foreground/background/style attributes; terminal data never enters HTML. Unknown local terminal palettes use standard xterm indexed colors. SGR `38;2` and `48;2` truecolor values pass through as `rgb()`. Without a tmux window style, the default colors are `#d0d0d0` on `#000000` (`renderAnsi` in `web/ansi.js`), because tmux cannot report the client terminal's own palette or default colors to the server. `web/navigation.js` owns session/pane selection and unread navigation; `web/app.js` preserves per-pane drafts/selections and freezes selected output. In each card's template the message form sits right after the output, so native Tab order goes from the output to the message box and then to the buttons; `order` on `.pane > .message-form` and `.pane > .feedback` in `web/style.css` keeps both at the bottom of the flex column on screen. The **Keys** chevron is a CSS `::after` on `.keys-toggle` that switches from ▸ to ▾ on `aria-expanded="true"`, which `web/app.js` sets when the row opens. A change in the screen rows above the input-marker row marks an inactive director-role pane unread, and an inactive manager-role pane only in a session without a director pane (`refresh()` in `web/app.js`; see the Browser teams part). `workArea` uses the last marker at or above the cursor. When either screen has an invalid cursor row or no such marker, the full output is compared instead. Worker and reviewer panes never mark unread, and initial history does not, because a new card has no previous capture. A roleless team's first pane counts as its manager. A session tab is unread when any of its pane cards is (`updateNavigation()` in `web/navigation.js`), so in effect only through its director, or through its manager when it has no director; viewing the pane clears it.

The font buttons set the CSS variable `--output-font` on `:root` and save the size under the localStorage key `peon-font`, clamped to 8..32. `refresh()` in `web/app.js` is the one place that measures cols and rows; the font buttons and a 150 ms debounced `resize` listener schedule it through `scheduleRefresh()`.

The regular poll `GET /api/panes` also carries `cols` and `rows`, the first `.output` of the visible card divided by the measured cell size, sent only within 20 to 500 columns and 5 to 300 rows, together with `session` and `pane`, the session and id of the visible pane. A poll runs about every 1.2 seconds, and a window resize schedules one after 150 ms. With `cols` and `rows`, `web/server.py` visits every session of the poll.

A detached session gets one tmux window per pane, because tmux sizes a window and panes that share it share its width. Only the session that `session` names is changed, and only when `pane` belongs to it. If the session option `@peon_pane_order` is empty, the server first records in it the pane ids of the `agents` window in their layout order. It then runs `break-pane -d` on every pane whose window holds more than one pane, which moves that pane to its own window named `p<number>`. `break-pane` keeps the pane id, so `send`, `msg`, and the watcher still reach every pane. Last, it resizes only the window of `pane` to `cols` by `rows` plus that window's border rows (`window_height` minus `pane_height`), and skips the resize when the window already has that size. A detached Claude pane keeps at least 12 content rows, matching the headless launch allowance for a stacked pane. Claude's input and footer can fill a shorter terminal and omit a table's top before it reaches tmux history. The browser still uses the requested row count to trim excess blank rows from its capture and can scroll the full text. A one-pane `agents` window keeps its top border row; a broken-out window has none. Other panes, other sessions, and a poll without `session` and `pane` get no resize. With several browser tabs open, the last poll for a pane sets its size.

An attached session gets its terminal layout back, whatever `session` names. When its `agents` window has `window-size` `manual` or a pane of the session is in another window, the next poll joins each outside pane into `agents` with `join-pane -d`, in the order of `@peon_pane_order`, or in pane id order when the option is empty. It then uses `swap-pane -d` until the panes stand in that order, unsets `window-size`, sets `main-pane-width` to 60%, applies `select-layout main-vertical`, and unsets `@peon_pane_order`. `goto_session` in `lib/session.sh` runs the same join, swap, and layout steps before it attaches or switches the client, so `peon-code <session>` opens on the terminal layout; it then unsets the option. A headless caller exits before these steps. Only these two paths join the panes. A client that attaches by hand sees the separate windows until the next poll that carries `cols`, about one second later while a browser page shows a card. With no such page open, the windows stay separate until `peon-code <session>` runs or a browser polls again.

Scrollback is a deeper live capture, not a store. Each card tracks its own depth `lines`, starting at 1,000. When the user scrolls up within 200 px of the top with no selection, and the last capture already reached the current depth, `web/app.js` adds 1,000 lines. It stops once the depth covers the pane's `#{history_size}`, which tmux's `history-limit` bounds and `web/bridge.py` reads with the pane identity, or at 200,000. The next poll adds `lines=<n>` to the `pane=<id>` of the visible pane only when the depth exceeds 1,000; `web/server.py` rejects a `lines` value outside 1,000 to 200,000 with 400, and captures only that pane with `capture-pane -S -<n>`, while other panes keep 1,000. Rendering waits until a capture reaches the requested depth, then keeps the view in place as the next paragraph describes. Within 40 px of the bottom the depth resets to 1,000. Polling continues at every depth, and nothing is persisted.

A screen scrolled up keeps its text in place while output grows. A screen within 40 px of its end follows the live output. For every other screen, `updateOutput()` calls `scrollAnchor()` in `web/app.js` before the render. `scrollAnchor()` finds the line at the top left of the visible text with `caretPositionFromPoint`, or `caretRangeFromPoint` where only that exists. From that line it moves down to the first line that is not blank and whose 3-line window, that line and the next two, occurs only once in the old text. If no visible window is unique, it uses the first non-blank visible line. It stops with no anchor when all visible lines are blank. It records the pixel offset of that line from the top of the screen. `updateOutput()` stores the capture start, `max(0, history - capturedLines)`, in `card.renderedStart` and counts only forward movement as rolled rows. After the render, the returned function finds each position of that window in the new text. It takes the match closest to the old index minus the lines that rolled off the top, plus the change in line count, and sets `scrollTop` so the line keeps its pixel offset. When all visible lines are blank or the new text has no match, the screen holds its distance from the bottom. When history size stops growing at tmux's history limit and no unique window is visible, the repeated-line fallback can move by one repeat period. Each screen keeps its own `anchorRemainder`, the fraction of a pixel that `scrollTop` rounding drops, and adds it to the next anchored scroll; a user scroll or the fallback sets it to 0.

Extra screens are a browser-only view of one pane; the server sees only the size of the first screen. In `web/index.html` each card holds a `.screens` column with one `.screen` that wraps the `.output`. The **+** button (`.add-screen`) clones the first `.screen` with its current DOM, appends a `.close-screen` button, and starts the clone at the bottom. `wireScreen()` in `web/app.js` attaches the same scroll, key, and context-menu handlers to every screen, all bound to the one card, so selection, explain, key sends, and depth growth act on that pane from any screen. `updateOutput()` renders the capture with `renderAnsi()` into the first `.output` only, then copies its child nodes into each other `.output` with `cloneNode(true)`. It measures and restores the scroll position of each screen on its own, and each screen keeps its last `scrollTop` for the scroll-up check. The depth resets to 1,000 only when every screen is within 40 px of its bottom. The **Stack order** button (`.stack-order`) flips `card.stack` between `'vertical'`, the default, and `'horizontal'`, toggles the `horizontal` class on `.screens`, which sets `flex-direction: row` in `web/style.css`, and restores each screen's scroll position. `refresh()` measures `cols` and `rows` from the first `.output`, so for a detached session a side-by-side split narrows the window of the viewed pane, and a vertical split shortens it. Other panes keep their size.

The screen layout of a card survives a reload in `localStorage` under the key `peon-screens:<session>/<pane name>`. `saveScreens()` in `web/app.js` stores `{stack, screens}`, with one `{anchor}` for each screen. `anchor` is null for a screen at the live output; otherwise it is the `scrollAnchor()` record `{text, pixelOffset, index, lineCount}`, where `text` is the 3-line window. Adding a screen, closing a screen, and the stack toggle write at once. A scroll writes after 300 ms with no further scroll, and `pagehide` writes any write that is still pending. The entry is removed when the card is one vertical screen at the live output, when the card is discarded, and when its pane is gone; a removal skips a key that another open card still uses. `createCard()` reads and validates the entry, sets the stack order, adds the saved screens, and gives each screen its saved anchor. The first `updateOutput()` passes that anchor to `scrollAnchor(output, saved)`, which finds the window in the new text as for a live render. When the saved text is not in the loaded history, the screen goes to the bottom. A read or write error in `localStorage` is ignored.

The HTTP server checks token, Host/Origin, and marked-session pane membership. `allowed()` accepts a `Host` header only when its hostname is loopback, `127.0.0.1`, `localhost`, or `[::1]`, with any port or none, and an `Origin` header, when one is sent, only as `http://` plus the same pattern. The port is not checked, because an SSH forward can land on another local port than the server's own. The hostname check guards against DNS rebinding, so a page served under a foreign hostname is still refused with 403, even when that name resolves to loopback. The token check applies only to authenticated paths and compares `X-Peon-Token` with `secrets.compare_digest` in `allowed()` in `web/server.py`. It reuses `explain` (`cmd_explain` in `lib/commands.sh`) and `send` via stdin and subprocess argument arrays, preserving safe-paste checks. The **Close session** button posts to `/api/dismiss`, which checks that the session is still in the pane list and runs `peon-code.sh dismiss <session>` with a 10 second timeout. Browser sends are serialized to avoid simultaneous empty-input checks.

Uploads go to `POST /api/upload?session=<s>&name=<n>&dir=<d>` with `Content-Type: application/octet-stream` and the raw file bytes as the body, 0 to 64 MiB (the `/api/upload` branch of `do_POST` in `web/server.py`). `do_POST` routes on `urlsplit(self.path).path`, so the query string does not affect dispatch. The server takes `projectDir` from a live pane of that session and refuses the request when no such pane exists. `name` must be a basename: not empty, `.`, or `..`, no `/` or `\`, no control characters, at most 255 UTF-8 bytes. `dir` defaults to `upload` when absent; it must be a relative path of at most 1024 UTF-8 bytes with no empty, `.`, or `..` component and no control characters, and trailing `/` characters are dropped. The folder must resolve inside the resolved project directory (`Path.resolve().is_relative_to`), so a symlink that points out of the project is refused. The server creates the folder on demand and writes with `open("xb")`, so it never replaces a file. It returns 200 with `Saved <dir>/<name>`, 409 when the file exists, 400 for bad input, a short body, or a folder path that is a file, and 503 for other `OSError`s. In the sidebar of `web/index.html`, the **Upload files** button `#upload` sits above **Swap agent** and works like it: class `swap`, `aria-expanded`, and `aria-controls="upload-form"`. It shows only while the current card is open, and an open form closes when the current card is gone or closed, or when the selection moves away from a card that is gone or closed; a move between two open cards keeps it open (`updateSwap()` in `web/app.js`). A click opens `#upload-form` (class `swap-form`) and focuses the **Folder** field, default `upload`; a second click, **Cancel**, or Escape closes it (`upload.onclick` and `openUpload()`). The form also holds a **Choose files** submit button, a hidden multiple-file input, and the `#upload-status` line. Submit opens the file picker instead of sending the form (`uploadForm.onsubmit`). `uploadFiles.onchange` sends one request per chosen file in order, with the trimmed folder or `upload` when the field is blank. It disables **Upload files** and **Choose files** until the last request ends, and writes one `<file>: <result>` status line per file, marked as an error when any file fails. After a batch, it saves the folder under the localStorage key `peon-upload-dir:<session>`; when the current session changes, `updateSwap()` restores that value, or `upload`, into the **Folder** field. Each time the form opens, `loadUploadFolders()` fills the `#upload-folders` datalist with the folder names of the project root listing. A revision counter drops a listing that returns after the session changed or the form closed, and a failed listing leaves the list empty, since a typed folder still works.

`#agents` holds the director tabs and one `details` group per team, described under [Browser teams](#browser-teams). `reconcileNavigation()` sorts panes by session, then by `roleOrder` (director, manager, worker, reviewer, then the rest), then by pane number (`web/navigation.js`). `#agents` takes `flex: 1 1 auto` with `min-height: 0` and `overflow-y: auto`, so the agent list scrolls and fills the free height, and the action buttons after it sit at the foot of the sidebar (the `#agents` rule in `web/style.css`). A sidebar form takes `flex-shrink: 1`, `min-height: 0`, and `overflow-y: auto`, so an open form scrolls inside the sidebar instead of pushing the buttons out (`.sidebar > form`). The sidebar's `padding-bottom` is the CSS variable `--pane-foot`, 0 when unset (the `.sidebar` rule). `updateSidebarFoot()` sets it to the height of the visible card below its `.screens` block: the card's bottom minus the bottom of `.screens`, which covers the action row, the keys strip, the message form, and the feedback line (`web/app.js`). So **Close session**, the last sidebar button, ends level with the bottom of the black `.output`. A `ResizeObserver` watches the visible card and its `.screens` and calls the same function, so the padding follows a keys strip that opens, a message box that grows, or a window resize (`sidebarObserver`). When the visible card changes, the function disconnects the observer and observes the new card; with no card the padding is 0. The wrapped `updateNavigation()` calls it after every navigation render. Below the 650 px breakpoint the sidebar takes `padding-bottom: 0`, its forms neither shrink nor scroll, and the list takes `flex: none` and `overflow: visible`, so nothing in the sidebar scrolls (the `@media (max-width: 650px)` block in `web/style.css`).

Two token-checked GET endpoints read the session project folder (`do_GET` in `web/server.py`). `GET /api/files?session=<s>&dir=<d>` lists one folder; `dir` absent or empty means the project root. `GET /api/file?session=<s>&path=<p>` returns one file, or one folder as a zip archive. Both go through `project_path()`, which applies the upload folder rules: a relative path of at most 1024 UTF-8 bytes, no empty, `.`, or `..` component, no control characters, trailing `/` characters dropped, and a resolved target inside the resolved project directory. Both accept the root. A path that breaks a rule returns 400, a missing path or a listed path that is not a folder returns 404, and another `OSError` returns 503. The listing reads `os.scandir` and calls `stat(follow_symlinks=False)`, so a symlink is type `other`, never `dir` or `file`. Each entry has `name`, `type`, `size` (files only), and `modified` in whole seconds. The server stops after 2000 entries in scandir order, then sorts folders first and names by `casefold()`, so in a larger folder the 2000 kept entries are not the first 2000 by name. The file endpoint follows symlinks that resolve inside the project, returns 404 for anything that is not a regular file, and returns 413 when the file is over 256 MiB (`MAX_FILE_BYTES`), checked on `stat` and again on the bytes read. It sends `Content-Type` from `mimetypes.guess_type`, or `application/octet-stream`, with no charset, and `Content-Disposition: attachment; filename*=UTF-8''<percent-encoded name>` (`respond()`). Every response also has `X-Content-Type-Options: nosniff`. When `path` names a folder, the project root included, the server sends a zip archive built in memory. It walks the folder with `os.walk(followlinks=False)`, so it does not enter a symlinked folder, and an error during the walk is raised to the same 404 and 503 handlers. It keeps only regular files by `lstat`, so symlinks and other file types are skipped, and it writes no directory entries, so an empty folder does not appear in the archive. It adds the `lstat` sizes as it walks and returns 413 as soon as the total passes 256 MiB, before it builds the archive. The cap counts uncompressed bytes, and the server does not check the size again when it reads each file. `zipfile.ZipFile` writes each member with `ZIP_DEFLATED`, under its path relative to the requested folder, and `strict_timestamps=False` lets files dated before 1980 in. The response has `Content-Type: application/zip` and the attachment name `<folder basename>.zip`, or `<project basename>.zip` for the root.

The browser cannot point an `img` or `iframe` at `/api/file`, because that request cannot carry the `X-Peon-Token` header. `fetchFile()` in `web/app.js` fetches the file with the header and the page shows the result through `URL.createObjectURL`. For this reason the Content-Security-Policy allows `img-src 'self' blob:` and `frame-src blob:` (`respond()` in `web/server.py`); all other sources stay at `default-src 'self'`. The **Download/view files** button `#files` shows and hides with **Swap agent** and opens the modal `#files-dialog` (`filesButton.onclick`). `loadFiles()` draws a breadcrumb that starts at **Project**, one row per entry, and a button that opens each folder row. Folder rows also get **Download**. File rows show the size in bytes and a **Download** button. The dialog header has a **Download** button for the current folder, which names the archive after the last folder segment, or after the project basename at the root. Names that end in `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.svg`, or `.pdf` also get **View**. `openFile()` shows **View** in the second dialog `#viewer`, in an `iframe` for a PDF and an `img` otherwise, and revokes that blob URL when the viewer closes. **Download** clicks a temporary `<a download>` on the blob URL, removes it, and revokes the URL after one second. For a folder, the client saves `<name>.zip`, and replaces that name with the decoded `filename*` of the response `Content-Disposition` when it can parse it. A failed download writes its error to the dialog status line. **Upload here** is disabled at the project root, because the upload endpoint needs a folder. In a subfolder it copies the current folder into the **Folder** field, closes the dialog, and opens the upload form (`uploadHere.onclick`). `fileDir` stays set after the dialog closes, so the dialog opens again at the last folder of the same session. If that folder now returns 404, the dialog falls back to the root. A different session starts at the root. The dialog closes when the session changes or the card closes (`updateSwap()`). Revision counters for the listing and the viewer drop responses that come back after a newer request or a close.

`buttons/*.md` holds the tracked prompt-button seeds. `web/server.py` defines `BUTTONS_DIR` as that installation directory. Its runtime `config_dir()` reads `XDG_CONFIG_HOME`, or defaults to `~/.config`, and appends `peon-code`; both PID files and custom button storage use it. Authenticated `GET /api/buttons` reads seeds and custom files from `config_dir()/buttons`, sorts by `(order, name)`, and returns file stems, one-line description frontmatter, and exact prompt bodies in a plain array. `order` is an optional frontmatter integer, 0 when absent; a value that is not an integer from 0 to 1000 makes the entry invalid. Invalid or unreadable entries are omitted independently; CRLF headers leave prompt bodies intact. `POST /api/buttons` validates the same fields, trims surrounding spaces from names, creates a custom file exclusively, rejects names already in either directory with 409, and returns the full array. Installation seeds are unchanged. The browser loads this list once and refreshes it after saving a button. Each pane renders the list and sends its prompt through `/api/send` without append.

The web shell launcher reuses `offer_update` before loading Python and restarts after successful pulls. Its SSH stdio mode emits an update event with a sanitized hostname; the client validates the event and hostname, prompts locally only with a TTY, and writes an explicit yes/no response. NonTTY local launches read update replies from `/dev/null`; the remote stdin channel remains open for server lifetime control after the handshake.

## The busy check

A pane's input box is read as everything from the prompt marker (claude draws `❯`, or `!` in shell mode, and codex draws `›`) to the end of the cursor's row, with the CLI's hint text left out, so text the cursor was moved back over still counts. `Enter` follows a paste only after two identical box reads 0.2 s apart, within 25 tries. The box must show the pasted text, leading CLI paste placeholders such as `[Pasted Content 1024 chars]`, or a message suffix. After leading placeholders are removed, any non-empty remainder must match a message suffix with spaces removed; a suffix without placeholders must have at least 100 characters. After Enter, `submit_paste` checks up to 10 more box reads, 0.2 s apart, and reports success only after a valid empty box read. A send that entered shell mode also accepts an empty shell-mode box as confirmation, and retries only when the shell command still matches the message without its leading `!`. When the message remains visible on two consecutive matching reads, it sends at most two extra Enters. Before any Enter, a failure still reports no Enter sent. After Enter, an empty box confirms success; a timeout, copy mode, changed agent, or refused retry reports Enter sent but submission not confirmed. The send command gives the reason. Message and brief callers use a separate status for this unconfirmed result, so they do not report the text as unsent or assume it remains in the box. The shared menu check also recognizes an anchored approval row ending in `(y)`, `(a)`, or `(n)` when its contiguous block has at least two choice rows, with the same cursor and quoted-marker guards. This check only decides whether a menu is open; the key command sends only Tab, Up, Down, Left, Right, Enter, Escape, BSpace, and C-c; the browser sends only Tab, Up, Down, Left, Right, Enter, Escape, Backspace, and C-c, so a choice is reached by moving the highlight, never by typing its digit or letter. The server maps browser Backspace to CLI BSpace. A focused pane output passes ArrowUp, ArrowDown, ArrowLeft, ArrowRight, Enter, Escape, and Backspace through as the matching keys (the output's `onkeydown` in `wireScreen()` in `web/app.js`). While a menu is open, the menu shortcuts replace the Up, Down, Enter, Escape, and Backspace buttons; the Left and Right buttons stay visible, because no menu shortcut duplicates them (`updateKeys()`). The browser sends C-c from Ctrl+C in a focused pane output only when no text is selected, so Ctrl+C still copies a selection, and it sends C-c even while that pane is busy with another send, because C-c is the interrupt; the Ctrl+C key button stays enabled while busy for the same reason, though it dims with the other buttons. During a send, every button on the page dims, Ctrl+C and the sidebar included. `send()` sets `card.busy` and calls `setSelection()`, which calls `updateBusy()`; that toggles the class `busy` on `body` while any card is busy or a team request is pending. The rule `body.busy button, body.busy summary` in `web/style.css` sets opacity `.45` with `transition: opacity 0s .3s`, the same as the `button:disabled` rule, and the `button, summary` rule restores full opacity with `transition: opacity 0s`, so the agent group headings dim with the buttons. So a send under 300 ms shows no change, and a longer one dims every button together. The dim is visual only. Blocking stays per button: `card.busy` disables the card's prompt buttons, add-button and its form, screen buttons, and Send (`setSelection()`), and `updateSwap()` gives **Swap agent**, **Download/view files**, **Upload files**, and the controls of both forms the same disabled state. A module-level `uploading` flag, set and cleared by the file input's `onchange` handler, keeps the upload button and form disabled when a refresh calls `updateSwap()` during an upload. Ctrl+C and the pane tabs (`tab()` in `web/navigation.js`) stay clickable while dimmed. Enter without `--submit` is refused unless the pane is on a menu, a check that runs inside the delivery lock before the key send.

## Folder trust

`launch_agents` (`lib/launch.sh`) writes trust before its per-agent loop, so no CLI starts first. The trusted paths are `pwd -P`, plus `$PWD` when the logical path differs. Each CLI's step runs once per launch and only when a team command starts with `claude` or `codex`. A failure prints a launch note and the launch continues; the CLI then shows its own dialog unless the config already trusts the path. A claude pane answers that dialog at launch (see [Briefs](#briefs)); codex leaves it to the user.

Claude: an inline `python3` script loads `${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json`, sets `projects[<path>].hasTrustDialogAccepted` to true with `setdefault`, so other keys in the entry survive, and writes nothing when every path is already true. A missing file or a missing `python3` skips the step; the file is never created. The write resolves symlinks with `realpath` and writes the target, so the link stays. It serializes to a `mkstemp` file in the target's directory, restores the original mode with `fchmod`, and commits with `os.replace`, so a failed write leaves the original intact. The whole file is re-serialized with two-space indentation.

Codex: the step resolves `${CODEX_HOME:-$HOME/.codex}/config.toml` through up to 40 `readlink` hops and writes the final target. If any line of the file assigns `projects` with `=`, bare or quoted key, as an inline `projects = { ... }` table does, the step prints a note on stderr and skips codex: TOML cannot add a `[projects."<path>"]` table to a table defined inline, so the append would make the file invalid. The match is a line-start `grep -E` and does not check which table the line sits in. Codex then shows its own dialog unless the file already trusts the path. Otherwise the path is escaped as a TOML basic string, and the step appends `[projects."<path>"]` and `trust_level = "trusted"`. The duplicate guard is a fixed-string `grep` for the path in double-quoted form, or in single-quoted literal form when the path holds no single quote or line break. A path the file already names is never appended again, so a user's explicit `untrusted` entry stays and a second table for the same key, which TOML rejects, is never written. The step copies the file with `cp -p` to a `mktemp` file in the same directory, appends, and moves it over the original. A missing file or directory is created; the new file gets the temp file's private mode.

## Briefs

`create_agent_session` passes `-e "PEON_CODE_SESSION=$session"`, `-e DISABLE_AUTO_UPDATE=true`, and `-e CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` to tmux `new-session` and `split-window` (`create_agent_session` in `lib/session.sh`), with support for tmux 3.2 and newer. Each pane inherits the session name. `DISABLE_AUTO_UPDATE=true` stops an oh-my-zsh update check, whose `read -k 1` at shell start would consume the first key of the pasted launch command. `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` keeps Claude's transcript in tmux history, because the alternate screen has no scrollback for `capture-pane` or the browser to read. `add_split_pane` in `lib/commands.sh`, which `add` and `add-team` share, passes the same three variables when it creates a pane with `split-window`.

`create_agent_session` starts the session detached at 220 columns by `agent_window_height <count>` rows, which is `12 * (count - 1) + 1` with a floor of 60 (`lib/session.sh`). Without a client, tmux would otherwise size a detached session at 80 by 24, and splitting that window for a large team fails with `pane too small`. `cmd_add` and `cmd_add_team` call `resize_headless_agents` with the pane count after the add, just before the first split. When the session has no client, it runs `tmux resize-window -y` to the same height, then sets the window option `window-size latest`, because `resize-window` switches the window to manual sizing; the next client that attaches sets the size again. With a client attached, it does nothing, so the terminal keeps its size.

After the trust step, `launch_agents` makes two passes over the panes. The first pass writes each brief file and sends each pane its launch command: a paste, a fixed one-second pause, then `Enter`, with no readiness wait except the shell check after the scope line described below. The second pass goes through the panes in order: it waits for the pane to leave the shell, and for a claude pane `claude_brief_after_start` answers the folder-trust dialog and then a resume picker, waits for the pane to settle, and pastes the brief. Both answers go through `answer_dialog` in `lib/tmux.sh`, which presses Enter only when the screen shows the cursor on the default row, `❯ 1. Yes, I trust this folder` for trust. It presses nothing when the cursor is on `No, exit` or when the input line is drawn first, and stops waiting after 15 seconds. It needs only bash and tmux, so it covers a trust step skipped for a missing `python3` or `.claude.json`. Because every CLI is already starting when the second pass begins, the waits on earlier panes overlap the startup of later ones; only the per-pane checks are serial. A pane whose launch command failed is not skipped: it times out in the readiness wait and joins the failed list.

Before the first pass, `launch_agents` probes once for a systemd user manager by running `systemd-run --user --scope -q -p OOMPolicy=continue -- true`; there is no OS check, so the probe itself is the gate. When the probe passes, the first pass pastes one extra line into each pane before its launch command, `systemd-run --user --scope -q -p OOMPolicy=continue -- "${SHELL:-sh}" -l`, then sleeps one second, calls `wait_shell_ready`, and pastes the launch command unchanged. The reason is that a tmux built with systemd support starts each pane in its own transient `tmux-spawn-*.scope`, and systemd gives that scope its `DefaultOOMPolicy`, which is `stop` unless the user manager sets otherwise (a tmux built without systemd support, and macOS, create no such scope): when the kernel out-of-memory killer takes any process in that scope, systemd stops the whole scope, so one killed child, such as a build or test the agent ran, takes down the pane shell and the agent with it. The nested login shell runs in its own scope with `OOMPolicy=continue`, so only the OOM victim dies, and because it is a login shell of the user's own `$SHELL`, the launch command resolves aliases and functions the same way it would in the outer shell. This has three limits. The agent process itself still dies when it is the OOM victim. Without `systemd-run`, or when the probe fails (macOS, or Linux without a user manager), nothing extra is pasted and the launch is unchanged. When the scope line fails inside a pane, the pane stays at the outer shell and the launch command runs there without the protection; the result of `wait_shell_ready` is not checked, so the one-second sleep is what gives `systemd-run` time to start the nested shell. Because a pane that is still inside a transient `systemd-run` has not reached the agent, `wait_agent_ready` in `lib/tmux.sh` counts `systemd-run` as a pane command that has not started yet, together with the shell names.

Every brief is written to a file in the session's brief directory, `${XDG_STATE_HOME:-$HOME/.local/state}/peon-code/<session>`, which the top-level code of `lib/launch.sh` creates with `umask 077` and records in the session option `@peon_brief_dir` and on every pane. The same directory holds the generated claude settings files, the add lock, and the watcher log. It lives outside the OS temporary directory, so a temp cleanup cannot remove the briefs of a running session. `cmd_dismiss` in `lib/session.sh` reads `@peon_brief_dir` before it kills the session and removes the directory afterward, but only when the path ends in `/peon-code/<session>`. A CLI that takes its prompt on the command line launches as `<cmd> "$(cat <file>)"`, so the command line stays one line instead of thousands of escaped characters. A pane can still open on a dialog, for example codex's folder-trust check when the trust step above could not write. A claude pane gets its brief pasted in once any dialog is gone, its input line is drawn, and the pane has stopped changing: any other menu or dialog counts as unsettled, so the launcher waits up to 30 seconds (2 minutes when resuming) and then names the pane in a status message telling you to run `peon-code rebrief <name>`.

A role pane's brief is the role file's body (its frontmatter stripped) followed by `roles/protocol.md` with the duties sections of the other types cut out, so the board and message rules appear once per brief and never inside a role file. The frontmatter `type:` selects the `## <Type> duties` section that stays, and the roster line shows every pane's type and description so each agent knows who dispatches, who works, and whether a reviewer exists. A roleless pane carries no protocol, so the shared brief spells out the claim, alert, completion, and stale-row rules for it; a role pane gets those only from the protocol, and the shared brief keeps just the send mechanics, the board header, and the numbered rules that are not about coordination. The config reader rejects a role file without a type and a team with roles that lacks a manager-type, a worker-type, or a reviewer-type role; a roleless CLI team skips the check.

## Write-ups

A writer never edits code: it reads the code for a single row inline, uses one subagent per row when it holds two or more rows, and writes one markdown file per subject under `innovation_summary/`. The role file fixes the shape of the output so the reviewer can judge it without a diff or a check to run: each innovation is one section with four labeled segments in order, Problem (what the code has to solve), Importance (why it matters and what it costs to get wrong), Innovation (the mechanism and the alternative it rejects), Implementation (how the code does it, with file paths and line numbers). The reviewer reads the output file directly, verifies every cited path and line, and fails the row when a segment is missing or the write-up tours files instead of naming a technique.

## Git denial

Only the main agent launches with full git. Every other agent launches with commit and the destructive git commands denied (`git reset`, `checkout`, `restore`, `switch`, `clean`, `stash`, `rm`, `commit`, `branch -D/-M/-f/--delete`, `push`, `rebase`, `reflog expire`, `update-ref`, `filter-branch`, `gc`): a claude pane gets a `--settings` deny file that also binds every subagent it spawns; other CLIs have no launch-time permission file, so they get a hard prohibition line in their brief, which their subagents do not see. Denying `git commit` on every other pane keeps commits in the main pane, which is what the shared brief rule tells the agents. The deny rules cover Bash commands only, not file writes, and a pane can rewrite the deny file or relaunch its CLI without it. The deny file goes only to a pane whose command starts with the literal token `claude`. The deny rules match literal command prefixes, so they do not block git invoked with a global flag such as `git -C <dir> reset` or `git --work-tree=<dir> clean`. A claude pane whose config line already passes `--settings` keeps that file and gets no deny file, and a pane passing `--dangerously-skip-permissions` gets the deny file but ignores it; both cases print a line to stderr at launch.

Agents draw on the normal screen so tmux keeps their scrollback for the browser's deeper captures. Codex gets `--no-alt-screen` appended after its own arguments unless that exact token is already there (`codex_launch_command` in `lib/cli/codex.sh`). Claude reads only one `--settings` file and a second would be lost (a comment in `claude_launch_command` in `lib/cli/claude.sh`), so the `"tui": "default"` key rides inside whichever file the pane already gets. `prepare_launch_settings` in `lib/launch.sh` writes both files in the session's brief directory: `deny-git.json` carries `tui` next to `permissions.deny` for every non-main claude pane, and `normal-screen.json` carries `tui` without deny rules for the main pane; `claude_launch_command` picks the file by `MAIN`. Both also carry the `statusLine` entry described under [Weekly limit](#weekly-limit). Both also set `promptSuggestionEnabled` to `false`, so a claude pane never draws grey hint text that an agent reading a capture could take for typed text. A pane that passes its own `--settings` gets neither file and a stderr warning that it may stay fullscreen. Nothing under `~/.claude` is written. Other CLIs get no normal-screen flag, so in alternate-screen mode only their visible screen is captured.

## Terminal title

The session sets `set-titles` for itself, so the terminal tab caption is `<session> : <directory>`, the directory being the base name of the active pane's current one. Other tmux sessions keep their own title setting.

## Resume lookup

Each brief carries the phrase `agent <name> of peon-code session <session>,`, trailing comma included, so one session name that is a prefix of another never matches the other's transcripts. `resume` searches each CLI's own transcript store for that phrase within the first 20 lines of a file (`head -n 20 | grep -F`), newest first, over the last 30 days: every `*.jsonl` file under `~/.claude/projects/<path>/`, `~/.codex/sessions/`, `~/.copilot/session-state/`, `~/.gemini/tmp/<sha256 of the working-directory path>/chats/`, and `~/.qwen/projects/<path>/chats/`, where `<path>` is the full working-directory path with every character other than letters and digits replaced by `-`. The codex and copilot stores hold every directory's transcripts, so a match there must also record the current working directory. The marker is unique per agent and session, so every pane reopens its own conversation rather than same-CLI panes landing in the newest one. A subagent's transcript can quote the parent's brief, so `last_thread_file` (`lib/resume.sh`) first asks the provider's optional `own_thread` concern about each candidate: claude rejects any path under a `subagents/` directory, and codex rejects a file whose first line carries `"thread_source":"subagent"` or a `"source":{"subagent"` object, which covers subagent forks and guardian reviews. Resume, the watcher, the crash and swap restarts, and the usage report all go through `last_thread_file`, so none of them takes a child thread as a pane's own.

## Context watcher

The command argument sets the initial threshold. Each scan reads the config path from the session option `@peon_conf` and checks its contents with `cksum`. When the path or checksum changes, the watcher reads `compact-at` without the config parser's fatal checks. A missing file, empty path, absent line, or value other than one nonnegative whole number keeps the current threshold. A changed threshold updates `@peon_compact_at`, clears the cached transcript readings, and emits one note through `watch_note`.

The launcher backgrounds `peon-code watch <session> <tokens>` with nohup before it attaches; the loop ends when `tmux has-session` fails. Each watcher tries to record its PID in `/tmp/peon-code-watch-$UID/<session>.pid`, with the directory and file created under `umask 077`. A failed write does not stop the watcher. Before starting a replacement, the launcher checks the recorded positive PID with `ps -ww -o args= -p <pid>` and sends TERM only when the full command identifies `peon-code.sh watch` for the exact session. On normal exit, a watcher removes the PID file only if it still records its own PID. Each watcher also writes its PID to the `@peon_watch_pid` session option at start and exits on a scan that finds another PID there, so after a resume recreates the session under the same name the newest watcher owns it and an older one stops within one scan. A scan runs every `PEON_WATCH_TICK` seconds (default 5); a floor of `PEON_WATCH_MIN` seconds (default 60) applies to both the shared transcript re-read beat and cached-path lookups; tests override both. Each scan lists the agent panes, reads the `@peon_bin` pane option the launch set, and for a claude or codex pane finds the transcript with the same marker lookup resume uses (`last_thread_file`). The lookup runs on the pane's first scan. An empty result is retried on every scan; a cached path is refreshed once the floor has passed since the last successful lookup. That lookup returns the newest marked file, so after a `clear` or a relaunch, which start a new transcript with the same marker, the watcher moves to it within one floor. When the lookup returns a path other than the cached one, the new path replaces it and the pane's last-read entry is dropped; an empty result clears the path and skips the pane until the next scan. A pane gets a full read on the scan that caches a new path and retries every scan until context tokens or usage appear. After that, it is re-read only when `wc -c` reports a changed size and the shared beat is due. Each scan takes one timestamp before reading the panes. When that timestamp is at least one floor after `last_beat`, every changed pane is read in that pass; after the pass, `last_beat` is set once to that timestamp, even if no transcript changed. A pane's startup read does not reset the shared beat. The transcript read state lives in three newline-separated shell variables inside `cmd_watch`: `files` holds `<pane> <path>`, `lookups` holds `<pane> <epoch>` of the last successful lookup, and `reads` holds `<pane> <size>` of the last full read with context tokens or usage. A full read writes the codex weekly figure (below) and takes the context size. The context size comes from the last usage record in that file: claude's assistant messages carry `usage` with input plus the two cache fields, codex's `token_count` events carry `last_token_usage.input_tokens`; both are the full request size the window limit applies to. A pane at or above the threshold is compacted through the `compact` subcommand, run with `TMUX_PANE` cleared so the watcher's own pane is never taken for a target, and is disarmed only after the slash command is accepted, until a later reading falls below the threshold, so a pane whose post-compact floor stays above it is compacted once, not on every full read. The watcher logs the compaction note only after compact succeeds. Failed attempts stay silent and drop the cached read so the next tick retries without waiting for a transcript change or the read beat. The screen is read for the working row and pending-brief readiness; context size still comes from the transcript. A scan with a positive compaction threshold also calls the optional `compact_count` hook when the transcript size changes, before the gate for full transcript reads. Claude counts lines with `subtype` equal to `compact_boundary` through `grep -c`. The `compacts` list stores `<pane> <size> <count>` and resets on a new transcript path or a pane restart. Its first read seeds the count. A later increase consumes and clears `@peon_compact_owned` without another brief when peon-code issued the compact, whether from the watcher, a terminal command, or the browser. A boundary with no ownership mark sets `@peon_rebrief_pending` to 1, including CLI auto-compaction or `/compact` typed directly in the pane. The next idle tick sends the pending brief through the existing retry branch. A CLI that does not log usage is named once and left to its own compaction.

The launcher starts the watcher when `compact-at` is above 0 or `restart-dead` is `yes`, and records the restart setting as the session option `@peon_restart` (1 or 0) right after it creates the session; the watcher reads that option once at start, so the `watch` command line still carries only the threshold. With a threshold of 0 the scan still checks for config changes and skips every transcript lookup and full read. In restart mode a scan lists every named pane, not only those running an agent, and keeps a `states` line of `<pane> <count> <hash>` per pane. A pane gets that line on the first scan whose `pane_current_command` is not a shell, so a pane whose agent never started is never restarted. On a later scan where the command is a shell name or `systemd-run`, the watcher hashes the visible screen with `cksum` of `tmux capture-pane`; the count resets to 0 when the hash differs from the last one and then goes up by 1, so a shell screen that holds still on two consecutive scans reaches 2 and marks the agent dead, and a screen that keeps changing, such as a user typing, never does. The command to run is the `@peon_launch` pane option, which `launch_agents` sets once per pane from `launch_command` with an empty resume id, so it never holds one; for codex it carries the brief through the prompt argument, for claude it does not. `watch_restart` then looks up the newest marked transcript with `last_thread_file`, limited to files newer than a reference file stamped with the session's creation time so a previous session's transcript is never resumed, and takes its id with `resume_id`. When an id is found and the provider's `resume_args` returns arguments, they go right after the binary in the stored command and the restart is a resume; otherwise the stored command runs as it is and the restart is fresh. Under the pane's delivery lock, `watch_launch_locked` sends `C-u` to clear any partial shell line and calls `launch_command_locked` from `lib/delivery.sh`, which pastes the command through `paste_only`, sleeps one second, and sends `Enter`; keys typed in that second can still join the command. The watcher then waits in `wait_agent_ready`, loads the brief from the `@peon_brief` file, and calls the provider's `brief_after_start` with the same globals the launch sets, so a claude pane answers the resume picker and gets its brief pasted, and a codex pane, whose brief is in its command line, needs no hook. The restart does not reuse the systemd scope line; the command goes into whatever shell the pane shows, which after a scoped launch is the nested login shell, though that the agent stays in the scope is not tested. Restarts run inside the serial scan, so a slow one delays the scan of the other panes. The cap lives in two more variables in `cmd_watch`: `restarts` holds `<pane> <epoch>` per attempt, and `capped` the panes already noted. Before an attempt the watcher drops entries an hour old or older and counts the pane's rest; at 3 it shows the cap note once and leaves the pane at the shell. Each attempt is recorded before its result is known, so a failed restart counts, and the window rolls, so the pane is tried again once its oldest entry ages out. An attempt also resets the pane's count to 0 and drops its cached transcript path, read, lookup, and disarm entries, so a restart that fails and leaves a shell is retried after two more still scans. A new watcher starts with empty counts. Both notes go through `tmux display-message` to the first attached client, or to the watch log when none is attached.

## Swap

`cmd_swap` (`lib/commands.sh`) checks its three fields against `^(-|[A-Za-z0-9._=/][A-Za-z0-9._=/-]*)$`, finds the pane by `@peon_name`, and reads the pane options the launch set: `@peon_cmd` holds the full agent command, `@peon_bin` its binary, `@peon_main` 1 for the main pane and 0 otherwise (it picks claude's `normal-screen.json` or `deny-git.json` settings file), and `@peon_launch` the launch command without a resume id that the watcher relaunches. A CLI can be swapped only when its provider defines the optional `swap_args` concern; `cli_call` returns 1 for any other CLI, and only claude and codex define it. For the same CLI, `cli_swap_args` (`lib/cli.sh`) splits the stored arguments into shell words in awk, keeping quotes, escapes, and command substitutions literal, drops only the provider's model and effort flags in their separate-word and `=` forms (an attached form such as `-mgpt-5` is kept), and appends the new ones through `swap_args`; for a different CLI the arguments start empty. The launch line then comes from the new provider's `launch_command` as at launch.

Before any change, `swap_reserve_locked` claims the pane under its delivery lock by setting `@peon_swap_owner` (the job's log path), `@peon_swap_identity`, `@peon_swap_started`, and the status text `@peon_swap` to `checking <command>`, and refuses a pane another live swap holds. `swap_start_job` starts `peon-code.sh __swap_job` detached with `setsid`, or `nohup` without it, so the caller returns at once. The job re-runs itself inside `systemd-run --user --scope -q -p OOMPolicy=continue` when that works, so the out-of-memory policy of the caller's pane scope does not reach it, and publishes its pid in `@peon_swap_pid`. It runs the probe from the optional `probe_command` concern, `claude -p "reply ok" --max-turns 1` or `codex exec "reply ok"` with the new arguments, from the project directory with stdin closed, in its own process group when `setsid` exists (and its own scope when `systemd-run` works); without `setsid` it is stopped with `pkill -P` and its pid. `swap_check` polls it 600 times at 0.1 s instead of calling `timeout`, which macOS lacks, then sends TERM as above, and KILL after one more second. Only the exit status counts. On failure `@peon_swap` becomes `failed: <detail>`, the last stderr line, `timed out after 60 seconds`, or the exit status, and a status-line note shows it.

On a pass the job writes folder trust with the new provider's `trust_project`, continuing with a note when that fails, and `swap_commit_locked` saves the brief and the `@peon_cmd`, `@peon_bin`, `@peon_launch`, `@peon_fresh`, `@peon_weekly`, and `@peon_usage` options to a backup file named in `@peon_swap_backup`. It rewrites the brief's identity line, roster line, and sender tags, sets the new command options, sets `@peon_fresh` to 1 only when the CLI changed, unsets `@peon_weekly` and `@peon_usage`, writes the marker `@peon_swap_pending` as `waiting <pid>:<epoch> <command>`, and sends the optional `quit_command` concern, `/exit` for both CLIs, through the same refusal checks as other slash commands. If the pane is not back at a shell within 30 seconds, `swap_abort_locked` restores the backup and the swap fails. With `@peon_restart` set to 1, the job then hands the relaunch to the watcher: `swap_handoff_locked` restamps the marker with the pid in `@peon_watch_pid`, retrying for 30 seconds, and fails with `no live watcher claimed the swap` when no watcher is running. With `@peon_restart` 0, the job calls `watch_restart` itself.

The watcher accepts a pane with a pending marker at a shell even when it never saw the agent running, and claims the marker as `running <pid>:<epoch>:<random> <command>`. A marker restart neither checks nor adds to the per-pane cap of 3 restarts an hour. `watch_restart_agent` skips the transcript lookup when `@peon_fresh` is 1, so a different CLI starts fresh, and otherwise resumes the newest own thread of the session as a crash restart does, so a same-CLI swap keeps its conversation when one is found; it then delivers the brief through `brief_after_start` and resets `@peon_fresh` to 0. `watch_swap_finish_locked` sets `@peon_swap` to `done <command>`, or a failed text when the agent did not become ready with its brief, and clears the marker. A marker is stale when its pid is dead, or when the pid is alive but is neither the session's `@peon_watch_pid` nor the swap job, whose command line must name the `@peon_swap_owner` log path. A `checking` status with no published pid counts as live for 10 seconds from `@peon_swap_started`. `watch_swap_reap_locked` runs from the watcher loop, from a new reservation, and before a restart; it aborts a stale waiting marker, restoring the backup when the agent still runs, and sets a failed status. `@peon_swap` is never unset; the next reservation overwrites it.

The browser posts to `/api/swap` with `pane`, `identity`, `cli`, `model`, and `effort` in a JSON body. `web/server.py` checks each field against the same token pattern as the shell, requires a CLI other than `-` to be in `available_clis()`, the `lib/cli/*.sh` files that define `<name>_swap_args` (also served at `GET /api/clis`), and requires the pane and identity to match a live pane. It runs `peon-code.sh swap` through `run_delivery` with `TMUX_PANE` cleared and a 20 second timeout. It answers 200 with the message on exit 0, 409 with the command's output otherwise, 400 for a field that fails validation, and 503 on a timeout or an OS error. `web/bridge.py` sends `@peon_cmd` as `agent_command` and `@peon_swap` as `swap`. `web/app.js` fills the form from `@peon_bin` and from the `--model`, `--effort`, and `model_reasoning_effort=` words of `agent_command`, so a codex `-m` flag leaves the model field blank. It sends `-` for a blank or unchanged field, and clears a `done` or `failed` state text 5 seconds after it appears.

## Add

`cmd_add` in `lib/commands.sh` runs in a subshell, so its `cd` and the launch globals it fills stay local. It takes `--session <name>`, `--team <name>`, and `--save` from any position and reads the other words as name, role, and command; command words after the first are quoted with `printf %q`. The name `director` is refused. The role resolves through `resolve_role` with the current directory as the config directory, before the `cd`, and its type must be manager, worker, or reviewer, as in a config file. The session must exist and carry the peon marker.

`add_lock` then takes the session's add lock, shared with `add-team`: a directory `add.lock` in the session's brief directory, created with `mkdir`, with the holder's pid in `add.lock/owner`. A second `add` or `add-team` that finds the lock fails at once and names the lock path. When the recorded owner pid is no longer alive, the caller first takes a `reclaim` guard inside the lock, checks the owner again, moves the stale lock aside into a `mktemp -d` directory, and removes it; a lock without a readable owner is never reclaimed. `add_cleanup` runs on `EXIT`: before the commit point it kills every pane the command created and deletes every board file it seeded, and it always removes the lock when this caller still owns it.

`load_session_agents` rebuilds the launch arrays from the session's panes. Each pane gives `@peon_cmd`, `@peon_role`, `@peon_team`, `@peon_main`, and `@peon_brief`, and the first pane that has one gives `@peon_brief_dir`. `initialize_agent_pane` in `lib/launch.sh` stores these options on every pane at launch for this reason. `add_roster_line` rebuilds each roster line from the stored role options, `@peon_role_label`, `@peon_role_type`, and `@peon_role_desc`, in the `pane <id>: <name> (<command>) - <label> (<type>): <description>` form the launch uses, because a custom role file may be gone. `load_session_agents` refuses a pane whose stored brief file is missing. `cmd_add` refuses a duplicate name, a second manager-type role in the target team, and a role agent in a team with no roles.

It then enters `@peon_project_dir`, runs `prepare_launch_settings`, and calls `add_split_pane`, which splits a new pane into the `agents` window with the same three environment variables as a launch, applies the given layout, initializes the pane, and waits for its shell. The new pane gets a `launch_agents` call limited to its index. Its brief file is `pane-<id>.md`, named from the stable pane id instead of an index, and it holds the full roster with the new line. If the launch fails or the agent never becomes ready, `add_cleanup` kills the pane and the command exits nonzero.

On success, `add_brief_note` appends `New teammate, add to the roster above: <roster line>` to each existing brief file through a `mktemp` copy and `mv`, so `rebrief`, `compact`, `clear`, and a watcher restart send the updated roster. Each existing pane then gets `[from peon-code] New teammate: <roster line>` through `cmd_send`; a refused send prints a note and does not fail the add. Last, `add_restart_watcher` runs when the session's `@peon_compact_at` is above 0 or `@peon_restart` is 1: it reads `@peon_watch_pid`, checks that process's arguments with `ps`, and starts `peon-code.sh watch <session> <threshold>` with `nohup` only when no watcher for that session runs.

The launch stores the config it read as the session option `@peon_conf`. `peon-code.sh` makes that path absolute after `load_team`, and sets it empty when agent commands on the command line replaced the config or no config file exists. `--save` picks its target before the new pane starts, through `session_config_path save`: the target is `@peon_conf` when that path is inside `@peon_project_dir`, is still a file, and is not the user config `$HOME/.config/peon-code/peon-code.conf`. For a later team, `team_config_path` reads the `team` lines of that config to find the team's own file. Any other case sets `rebuild` and targets `<project>/peon-code.conf`, which must not exist yet, not even as a symlink; a session of several teams refuses the rebuild. When the target file does not exist, `add_root_roles` checks that each current pane's `@peon_role_label` names a shipped role or a file in `roles/` next to the target, and records that label, or `-` for a pane without a role type. `add_saved_role` saves a role given as a path that is not a shipped file under its label, which must match `[A-Za-z0-9_-]+` and must not be a shipped name; its copy target is `roles/<label>.md` next to the config, and an existing target must match it byte for byte under `cmp -s`.

The write runs after the launch and the teammate notes. It repeats the existence checks, so a file that appeared during the launch is still refused. A failure in this step exits nonzero and leaves the new agent running, unsaved. `add_copy_role` copies the role file with `mkdir -p` and `cp` only when no identical copy exists. `add_config_append` starts the new config in a `mktemp` file next to the target, copying an existing config first with a newline added when its last byte is not one; the command then moves it over the target, so the result has the temp file's private mode. A rebuilt config instead gets one `name command role` line per existing pane, with `*` on the `MAIN` index. The new agent's line follows, and for team 1 `@peon_conf` is set to the target, so a second `--save` appends to the same file.

## Teams

A session of several teams is one flat set of launch arrays. `read_conf <file> <nested> <team>` in `lib/config.sh` fills two more alongside `NAMES`, `CMDS`, and `ROLES`: `TEAMS` holds each agent's team name, and `TEAM_NAMES` the distinct names in order. `load_team` seeds `TEAM_NAMES` with the session name, so team 1 is named after the session, and command-line agents join that team. A `team <name> <file>` line checks the name, refuses the session name and a name used twice, appends it to `TEAM_NAMES`, and calls `read_conf <file> 1 <name>` on the path resolved against the config's directory.

The nested call reads agent lines only: it skips a `team`, `compact-at`, or `restart-dead` line with a warning on stderr, ignores a `*` mark, and prefixes each name with `<team>-`, so names stay unique across the session and team 1 keeps bare names. A line whose first word is `director` is refused in every file, because that name is reserved for the director pane. The director-type refusal for agent lines lives in the role check of `read_conf`, so only the launcher's own pane carries that role. The manager, worker, and reviewer check runs per call over the agents whose `TEAMS` entry is that call's team, so each team must be complete on its own.

After the top-level file, two or more team names append one agent named `director` with the shipped `roles/director.md` and an empty `TEAMS` entry. Its command is that of team 1's first manager, or of team 1's first agent when team 1 has no roles; there is no config line for it, and `swap director` changes it later. `MAIN_INDEX` points at it, which overrides any `*` mark.

The main-slot rule in the top-level code of `lib/launch.sh` takes `MAIN_INDEX` first, else the first manager-type role, else pane 0. The director wins only because `read_conf` set `MAIN_INDEX`. `@peon_main` then follows `MAIN`, so the director is the one pane that runs claude with the normal settings file, and every team manager gets the git denial from `claude_launch_command` in `lib/cli/claude.sh`.

`initialize_agent_pane` stores the team in the pane option `@peon_team`, but only when `TEAM_NAMES[1]` exists; a one-team session stores an empty value, and the director always stores an empty value. The window's `pane-border-format`, set in `create_agent_session` in `lib/session.sh`, prints `<team>/` before the name only when `@peon_team` is set, so a one-team session shows the name alone. The roster is one list for the whole session: each line keeps the `pane <id>: <name> (<command>) - <label> (<type>): <description>` form, so the prefix that swap rewrites matches every line, and in a session of several teams a ` [team <t>]` tag follows it. Every agent therefore sees every pane.

When the main pane is the director, `build_brief` in `lib/brief.sh` gives every other pane the team sentence: it names the pane's team, limits messages to that team and the director, and says the director handles git and talks to the user. The sentence is printed right after the role section. The same condition sets the target of rules 3, 4, and 5 to the director for a manager-type or roleless pane, and to the pane's team manager for any other type, so a held send, a dead pane, or a deadlock goes up one level instead of to the user. Rule 1 for a director main pane names the director pane for intake, the plan board, and the dispatch to team managers, and says the director posts the final summary. Rule 2 names the main pane, the director in such a session, as the commit pane, and in the director's own brief it says to stage only the files listed in the plan rows it has checked. Rule 10 drops its claim sentence for a manager-type or director-type pane, because neither claims rows.

`board_for <i>` picks each pane's board: `.peon-code-plan.md` for the director, `.peon-code-task.<team>.md` for a team other than `TEAM_NAMES[0]`, and `TASK_BOARD` otherwise. `build_brief` names that file in the board paragraph, and `seed_board` writes every file it returns that is missing, with the header from `board_header_for`. `PLAN_HEADER` is `BOARD_HEADER` with `T1, T2` replaced by `D1, D2` and one sentence added before the status rule: only the director edits the plan board, and the manager in the who cell reports its row by message. `board_header_for` returns `PLAN_HEADER` for the director. For any other pane in a session whose main pane is the director, it returns `BOARD_HEADER` with a sentence that every task cell starts with the plan row id it serves; otherwise it returns `BOARD_HEADER` unchanged. The same function feeds the launch seed, the `add-team` seed, and the recreate instruction in each brief. The plan board rules, the D id prefix, and the plan dispatch, plan done, plan blocked, plan findings, and plan withdraw messages are defined in `roles/protocol.md`.

### Add team

`cmd_add_team` in `lib/commands.sh` runs in a subshell like `cmd_add` and takes `--team`, `--save`, and `--session`. `session_config_path source` returns `CONF` from `-c`, else the session's `@peon_conf`, made absolute; it must exist. The command then takes the add lock with `add_lock` and rebuilds the arrays with `load_session_agents`, reading an empty `@peon_team` as the session name. The default team name is the first `team<n>`, counting from `team2`, that the session does not use. The source config goes through `read_conf` with `nested=1`, so only its direct agent lines count, a file with `team` lines still yields one team, and the role check of `read_conf` applies.

When the session has no `director` pane yet, the command appends one. The current main pane must be manager-type, and the director gets that pane's command. `MAIN` moves to the director. The roster is rebuilt for the old panes. `resize_headless_agents` sizes the window for the new pane count, and each new pane goes through `add_split_pane` with the `tiled` layout, gets its roster line, and gets its board from `seed_board`; a board the command created is recorded so `add_cleanup` can delete it. `launch_agents` runs once per new index; any failure dies, and `add_cleanup` kills every created pane and deletes every created board while `committed` is 0, so the old panes and their briefs are untouched.

After the new agents start, `add_team_convert_director` handles a new director. It swaps the director pane with the first pane of the `agents` window, so `main-vertical` puts it in the left slot, and prepends its id to `@peon_pane_order` when that option is set, so the browser's rejoin order also starts with it. It sets `@peon_team` on every old pane to the session name and flips the old main pane's `@peon_main` to 0. It rebuilds that pane's `@peon_launch` with the CLI's `launch_command` while `MAIN` names the director, so a restart or a swap brings the old manager back under the git denial. When the rebuild fails or returns nothing, it unsets `@peon_launch`, which turns off the automatic restart of that pane, and warns on stderr to swap it before restarting. The running process keeps the settings it started with, and stdout says that the manager keeps git until it is swapped or restarted.

`add_brief_note` then appends the new roster lines to each old brief file, plus, for a new director, a notice. The notice says it replaces rules 1 and 2. It names the director pane for intake and git, names the old team as the session name, the roster lines without a `[team]` tag, and limits messages to that team and the director. It says that where rules 3, 4, and 5 say tell the user, the pane tells the director, that team managers report plan rows as `D<n> done` to the director, and that the director posts the final summary. It forbids `git commit`, `git stash`, and any history-rewriting git command, says to request commits from the director, and names the director pane as the commit pane. Last, `rebrief_agents all <session> <old pane ids>` pastes the updated briefs into the old panes only; its third argument limits it to those ids, since the new panes got their full brief at launch. A pane the rebrief skips keeps the updated brief file for a later `rebrief`.

`add_team_save` runs when `--save` was given. Its checks run before any pane starts, and it writes after the rebrief. The team goes to `<project>/peon-code.<team>.conf`, one `name command role` line per new agent with the `<team>-` prefix stripped, and custom roles are checked by `add_saved_role` and copied by `add_copy_role`, which `cmd_add --save` shares. The session config gets `team <name> <file>`, with the file path made relative to the config's directory. With no usable session config in the project, the command rebuilds `peon-code.conf` from the team 1 panes, with `*` on the old main pane, and writes one `peon-code.<team>.conf` per other running team with a `team` line for each. Every target file must not exist, and the checks repeat just before each `mv`. `@peon_conf` then names the saved config. `add_restart_watcher` runs last, as in `cmd_add`.

`cmd_add --team` adds to one team: the default is the team of `TMUX_PANE`, else team 1; the name gets the team prefix, and the one-manager check runs only over that team's panes. For a later team, `--save` finds that team's file with `team_config_path` and leaves `@peon_conf` unchanged.

### Browser teams

`web/bridge.py` reads `@peon_team` as a `list-panes` field and sends it as `team`. It accepts `director` as a role type, including in the brief fallback for panes without `@peon_role_type`, and sorts each session director, manager, workers, reviewer.

The sidebar in `web/index.html` has a `#director-tabs` list above `#team-groups`. `updateNavigation()` in `web/navigation.js` puts director panes in the first list and builds one `<details>` per distinct `pane.team || pane.session`, so a one-team session shows one group named after the session. The groups are rebuilt only when the session or the team list changes; each group's open state is saved in `navigation.groups` under the key `[session, team]`, so a collapse survives polls and session switches. `agentTab()` labels every tab with the name and a type letter, `(D)`, `(M)`, `(W)`, or `(R)`, ahead of the token figure. A collapsed group's summary takes the unread, needs-answer, and waiting-text flags of any pane inside it, so a hidden pane still signals. Each poll, `refresh()` in `web/app.js` builds `directorSessions`, the Set of sessions that hold a director-role pane, once. A work-area change then marks a director pane unread, and marks a manager pane unread only when its session is not in `directorSessions`; so in a session with a director only the director tab flags unread, and in a session without one the manager pane flags unread. The card meta line adds the team.

**Add team** (`#add-team`) is a sidebar button of class `swap`, and its form `#add-team-form` is a `.swap-form` right below it, like **Swap agent** and `#swap-form`. The form holds **Team**, a text field whose placeholder names the default, `team2`, `team3`, and so on; **Save**, a `select` with **Yes** and **No**, Yes first, so the submit sends `save` true only for `yes`; and the **Choose config** button, with no label, in front of a hidden file input. The button clicks the input unless it is disabled. `#team-config-name`, a `.swap-state` span with `role="status"`, reads `No config: copies this team` until a file is chosen; the input's `change` handler writes the file name into it, or puts the hint text back when the choice is empty, and `hideForm` puts the hint text back too. `#add-team-status`, also a `.swap-state` span with `role="status"`, holds the request state. A `web/style.css` rule gives both spans the full form width, no left margin, left aligned text, and `pre-line` wrapping. A form's submit button repeats the verb of its toggle: **Add** under **Add team**, **Swap** under **Swap agent**. `updateAddTeam()` shows the button while the current card is open, and disables it and every `input`, `select`, and `button` of the form while that card is busy, a swap runs, or a team request runs. It closes an open form when the card is gone or closed, or when the current session is not the one the form opened for. A click closes the swap and upload forms, stores the session in `teamSession`, clears the status span, and focuses the team name; a second click, **Cancel**, or Escape closes the form. `hideForm(button, form)` closes the upload, swap, and add team forms alike; for the add team form it also resets the fields, puts the hint text back in the file name span, and clears `teamSession`. When focus was inside the form, on its button, on an output, or on the body, it moves focus to the button, or to the current card's output when the button is hidden or disabled. Opening one form runs `closeOtherForms()`, which hides the other two, and opening the file browser hides all three. On submit, `teamPending` and `card.busy` dim the page through `body.busy`, which `updateBusy()` sets. The body is `session`, `team`, `save`, and the optional upload read by the same `configFields()` as the new-session form. It goes to `/api/team` with no folder-create retry. The status span shows `Adding team...`, then the result message, or the error with the `error` class, and the card feedback line shows the same text. On success the form closes if it still belongs to that session, and the page refreshes.

`/api/team` shares the `/api/open` branch of `do_POST` in `web/server.py` and its 2 MiB limit. It requires a live `session` and a team name that matches `[A-Za-z0-9_-]+` and is not `director`, and it ignores `create`. An upload is always written to the uploads directory, never into the project, because `--save` belongs to `add-team`. The server then runs `peon-code.sh [-c <config>] add-team --session <s> [--team <name>] [--save]` through `run_delivery` with a 300 second timeout, and answers 200 with the last stdout line or 409 with stderr. On a timeout, `run_delivery` kills the process group, and the server answers 503 with the fixed text `Team did not start within 5 minutes; check the tmux session for half-built panes`, never the command line. Without an upload there is no `-c`, so `add-team` reads the session's `@peon_conf` and clones its direct agent lines, team 1.

## Usage report

`print_usage` in `lib/session.sh` backs both `usage` and `dismiss`, which prints it before `tmux kill-session`. Token counts are an optional provider concern, `usage_tokens`: called with no arguments it returns 0 when supported, and the `cli_call` fallback returns 1 for a CLI without it, which the report shows as no usage logged. Called with a transcript path it prints four integers, input, cache read, cache write, and output, or nothing when it finds no usage. The transcript comes from the same marker lookup the watcher uses: `last_thread_file` with `agent <name> of peon-code session <session>,`, run from the pane's current path. That lookup returns one file, the newest own transcript modified in the last 30 days with the marker in its first 20 lines, so an agent's earlier conversations are not counted. `cli_usage_sum` (`lib/cli.sh`) adds the threads that file spawned: it parses the own file, then every path the optional `child_threads` concern prints, skipping a child that has no usage and any path already counted, which a list of seen paths compared one by one enforces. `claude_child_threads` lists `agent-*.jsonl` under `<session id>/subagents/` beside the own transcript. `codex_child_threads` reads the `session_meta` line of every `*.jsonl` under `${CODEX_HOME:-$HOME/.codex}/sessions` modified in the last 30 days, takes its `payload.id` and `parent_thread_id`, and walks breadth first from the own thread's id to depth 5, keeping its own seen list so a thread reached twice is listed once. The search covers the whole sessions tree, bounded by the 30 days and the depth, not by date directory. The context size and the weekly limit still come from the own file only. Claude's transcript repeats a request's usage across the lines of one response, so `claude_usage_tokens` keys each `usage` object by its `requestId`, keeps the last one per id, and sums over the unique ids: `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, and `output_tokens`. Codex's `token_count` events carry a cumulative `total_token_usage`, so `codex_usage_tokens` takes only the last one. Its `input_tokens` includes the cached part, so the parser subtracts `cached_input_tokens` from input and shows that part as cache read; cache write is its `cache_write_input_tokens`, which current codex transcripts record as 0, and a missing key also prints 0. Both parsers scan lines with awk patterns rather than parsing JSON. The per-CLI totals are summed in one awk pass over the agent lines.

## Weekly limit

The `@peon_weekly` and `@peon_usage` pane options are the two hand-off points between the bash side and the browser. `@peon_weekly` holds `<used percent> <reset epoch seconds>`, such as `42.0 1760000000`, with the percent held to one decimal and clamped to 100 by each writer. There are two writers. For codex, each full read of the watcher calls the optional `weekly_limit` provider concern on the transcript it already found: `codex_weekly_limit` takes the last `token_count` line, looks at its `rate_limits` `primary` then `secondary` entry, and uses the first whose `window_minutes` is 10080, printing `used_percent` and an integer `resets_at`. The `cli_call` fallback returns 1 for a CLI without the concern, and the watcher writes `@peon_weekly` only for a non-empty result, so it never clears a value another writer set. For claude, the launch reads `.statusLine.command` from `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/settings.json` with `python3` and adds a `statusLine` entry to both generated settings files, `normal-screen.json` and `deny-git.json`, whose command is `peon-code.sh statusline` followed by the shell-quoted user command; the entry holds only `type` and `command`, so other keys of the user's `statusLine`, such as `padding`, are dropped. Only that user settings scope is read; a status line set in project or local settings is replaced by the wrapper and not run. Without `python3` no `statusLine` key is written. A pane that passes its own `--settings` gets none of the generated settings, the wrapper included, and the launch says on stderr that its weekly limit is not recorded. `cmd_statusline` (`lib/commands.sh`) reads all of stdin, keeping trailing newlines, takes `used_percentage` and an integer `resets_at` from the last `"seven_day":{...}` object with `sed`, writes `@peon_weekly` on `$TMUX_PANE`, then runs the user command with `sh -c` on the same stdin bytes and leaves its output and exit status untouched. `web/bridge.py` reads `@peon_weekly` as one more `list-panes` field and accepts it only when the percent is finite and between 0 and 100 and the reset is all digits; anything else sends `weekly: null`. A reset time already past reads as 0% used, since the limit has reset but no new reading has arrived. `web/bridge.py` also sends the `@peon_bin` pane option, the first word of the agent command that the launch set, unchanged as the `cli` field, an empty string when the option is unset. `web/app.js` appends `<cli> weekly <100 minus used>% left, resets <local time>` to the card meta line, without the `<cli> ` prefix when `cli` is empty, and nothing when `weekly` is null.

`@peon_usage` holds `<input> <cache read> <cache write> <output>`, four integers separated by single spaces. Its one writer is the watcher: each full read runs `cli_usage_sum` on the transcript it already found, the same own plus child sum `peon-code usage` uses (`print_usage` above), and writes the option only when the result matches four digit runs, so a failed parse leaves the last value in place. The watcher moves to a newer marked transcript within one floor (see [Context watcher](#context-watcher)), so after a `clear` the option describes the new conversation once that transcript holds a usage record; until then the last value stays. `web/bridge.py` reads it as one more `list-panes` field and sends `usage: {input, cacheRead, cacheWrite, output}` when it splits into exactly four all-digit fields, otherwise `usage: null`. `web/navigation.js` sums the four and labels the sidebar tab `<name> · <total>`, or `<name>` alone when `usage` is null. The unit is chosen by the rounded value, so the M cut is 999950 and the B cut is 999995000.

## Update check

On a start or resume, `offer_update` in `lib/config.sh` asks for the newest commit of the upstream branch with `git ls-remote`, which changes no local ref. It asks `PEON_UPDATE_URL` first, then the clone's own remote when that fails or replies empty, printing a notice naming both. The public probe is always capped at `PEON_FETCH_TIMEOUT` with `GIT_TERMINAL_PROMPT=0`; the remote probe is uncapped and may prompt only when stdin is a terminal and the mode is not stdio; otherwise it has the same cap and `GIT_TERMINAL_PROMPT=0`. The cap is a portable poll loop (`kill -0` every 0.1 s, then TERM, then KILL after 1 s), not coreutils `timeout`. Both failing prints a failure line and starts the current version. There is no offer when the answer equals `HEAD`, is an ancestor of `HEAD`, or is a local commit that `HEAD` does not precede (diverged); a hash missing locally still gets an offer, and an ff-only pull then fails on divergence. The offer reads `update available upstream; pull now? [y/N]`, or a JSON line in stdio mode, which `web/launch.py` turns into a prompt on the Mac for `--ssh`, after the Mac's own check. The pull is `pull --ff-only` from the source that answered: from the URL with an empty `--refmap` so no tracking ref moves, or from the remote followed by `update-ref` of the upstream ref. A `y` pulls, prints `updated; starting`, waits three seconds (`PEON_UPDATE_PAUSE` overrides it for tests) so the outcome is read before the screen moves on, and restarts the launcher with the same arguments, because bash reads the script lazily and a file rewritten under it can execute a mix of old and new lines. The check is synchronous, so a start waits up to the cap per capped probe, and a push shows up on the next start. The other subcommands never touch git.

## Command details

These are the edge cases of each subcommand that a user meets only on the failure path.

- Version: `peon-code --version` prints the `VERSION` file at the top of the clone, and the first line of `peon-code -h` shows it as `peon-code <version>`; without that file both show `unknown`. When the clone is its own Git repository and `core.hooksPath` is not set there, `install.sh` sets it to `.githooks` and prints `installed Git hooks: .githooks`; an existing hooks path is kept and printed as `kept Git hooks: <path>`. The `pre-commit` hook raises the last number of `VERSION` by one and stages the file on every commit, an amended commit included. A `VERSION` that is not three plain numbers joined by dots stops the commit; `git commit --no-verify` skips the hook.
- Uninstall: both links are checked before either is removed. A foreign command at either path is left alone and the command exits 1; nothing there at all exits 0.
- Launch: the session is attached as soon as its panes exist, so the CLIs start while the session is on screen. A run from inside tmux switches that client to the new session. The CLIs start one after another, about a second apart, or about three seconds apart with the systemd scope line; the per-pane checks then run one at a time, so a pane that times out or waits on a dialog adds its full wait. With a terminal, a failed agent is named on the status line and the session stays up with the failed pane in view. Without a terminal, the launcher prints `tmux attach -t <session>` and exits 0, or kills the session and exits nonzero when an agent fails.
- Resume: a resumed claude pane that opens on the "Resume from summary" picker takes the summary default and waits out the compaction before its brief is pasted. Every resumed pane gets its full brief, since pane ids change with each session.
- `detach`, `dismiss`, `usage`: `detach` exits 1 when the session is missing or not a peon-code session. `dismiss` and `usage` say so and exit 0 for a missing session, and exit 1 for a foreign one. `usage` shows `no transcript` for an agent whose conversation file is not found.
- `list`: exits 0, with or without agent panes; an argument exits 1.
- `msg`: panes are taken one at a time, each getting up to about 3 seconds for its box to show the text before `Enter`. Text the box took but never showed stays there for the user to submit. An unknown agent name prints the session's panes and exits 1, and a run where any pane took no message exits nonzero.
- `send`: a busy target is retried up to 10 times over about 10 seconds. A pane back at a shell, a pane peon-code did not launch, and a pane with no known prompt marker exit nonzero at once.
- `rebrief`: a skipped pane, including one from an older launch with no stored brief, gets a note on stderr and on its own does not change the exit code.
- `compact`, `clear`: when the caller's own pane is among the targets, no pane is sent anything and a note says to run the command from a shell or another pane. A box that holds anything other than the slash command after the paste gets no `Enter`. The run exits nonzero only when no pane took the command.
- `swap`: each field must be one plain token; the effort is not checked against a list, so a value the CLI rejects fails the test run. The composed command must differ as text from the stored one, so a reordered or respelled flag still runs a full swap. The command returns as soon as the test run starts, and the pane is marked checking, then failed with the last error line, a timeout, or the exit status, or done. A passing swap writes folder trust for the new CLI, clears the pane's usage and weekly figures, and sends `/exit`; the watcher relaunches the pane, or the swap does with `restart-dead no`. A swap does not count toward the watcher's restart cap. A swap of a pane at its shell, or while another swap of that pane is checking, is refused.
- `add`: refuses a team whose panes have no stored brief, and starts a watcher when the team uses one and none runs. `--save` refuses when the project folder holds a `peon-code.conf` the session did not launch from, when `roles/<name>.md` holds different content, or when a shipped role has that name. A new config needs every role of the roster shipped or present in `roles/` next to it. For a later team, `--save` needs a saved session config with that team's `team` line.
- `add-team`: with no session config in the project folder, `--save` writes `peon-code.conf` for team 1 plus one `peon-code.<team>.conf` per other team. If any new agent does not start, every new pane is killed. Running agents get the new roster and are briefed again.
- Watcher: a restart follows about 5 to 10 seconds after the exit, with a status-line note that says resumed or started fresh. At the cap of 3 attempts in a rolling hour, failed attempts included, a note says so and the pane stays at its shell until the hour passes; a new launch starts a new count. The pane keeps its id, so the browser shows the relaunch without a reload.
- Browser: a noninteractive `--dir` launch stops when the folder is missing. An existing team opens only if it is a peon-code team for the same folder; a team of that name in another folder reports a collision. With `--config`, an existing team opens unchanged, and over SSH the remote user config stays unchanged. Over SSH without `--port`, the remote server takes the first of the twenty ports that is free or held by the user's own earlier `peon-code-web` server, which it stops; when other programs hold all twenty, the launch fails, and an older remote install that does not know the port range fails too. With `--port N` over SSH, both ends use only port N; `--port 0` takes a temporary port for local tests. Over SSH the Mac runs its own update check first, then the remote host checks and its prompt shows in the local terminal; the remote check never asks for credentials, and a noninteractive launch declines the update. The page remembers the last upload folder per team in that browser only.

## Task board protocol

The board file opens with a header stating the editing rules, above a table of `id | who | task | files | status`: one row per task, edited in place by its owner; ids (`T1`, `T2`, ...) are assigned by the row's creator and never reused; the status cell holds exactly one of in progress, done, reviewed pass, reviewed fail, and a status change overwrites the cell rather than appending to it; findings travel by message, not on the board. Because the header rides in the file, agents re-read the rules every time they read the board, so the rules survive a clear or compact. The row is the claim: an agent writes its claim before starting, sends no start message, and does not touch files another agent listed. Messages are alerts, one line naming the row id (`T3 done`, `T3 blocked: ...`); the board is the record that lasts. Edits that fall at the same moment, like several claims at launch, go in one edit, but a status change is never delayed to batch it with another. An agent sets its own row to done before sending its completion message; a message never substitutes for the row edit. A row the reviewer sets to reviewed fail goes back to its author: the author sets it to in progress for the rework and to done when the fix is ready, and a row back at done counts as unreviewed and gets a fresh review. The main pane's brief adds a verification duty: on a completion message it checks the sender's row and sets it to done itself if the sender did not, before dispatching new work, and it dispatches with one message per agent listing that agent's row ids. Once the reviewer records reviewed pass it deletes the row; the deletion is the acknowledgment, so the board lists only open work. After a clear, compact, or rebrief, an agent trusts a row only if its status matches reality, and confirms with the owner before redoing work a row shows as still open but that already looks done. A lost done message does not stall the team: a manager acts on every row at done or reviewed pass whenever it gets any message or reads the board, and a director whose manager stays silent reads that team's board and relays a finished row to the manager by message. A worker whose send fails retries once, then sends the line and the exact send error to the other recipient of that message (the reviewer for a manager, and the reverse), and reports to the pane its brief names only when no recipient is reachable.
